# Состояния партии

Карта машины `src/game/machine.ts` (XState 5, id `game`). Условия, счёт и табло — в списках ниже. Текст — источник; mermaid-схемы при каждой правке не перерисовываются (если нужна диаграмма, её рисуют по состоянию кода на момент просьбы).

Контроллер (`src/game/controller.ts`) сам счёт не меняет. Он шлёт события машине, включает микрофон и обрывает звук ведущей. Где это меняет фазу или часы, это написано у перехода.

Полоска на табло есть только когда заданы и `phaseStartedAt`, и `phaseDurationMs`. Отдельные `after`-таймеры (моргание, раннее окно, оценка, ставка) полоску не рисуют.

Кнопки ответа открыты, когда `buttonsLive`: `reading.armed`, `falseStartCue` и любой `buzzing.*`. Фальстарт возможен только в обычном раунде и только в `flashing` и `reading.sealed`.

## Маршрут

Узлы ожидания описаны ниже. `restoring`, `afterReading`, `finalBets`, `turnCue` и `finalTyped` ждут по таймеру фазы; `choosing`, `reading`, `finalReveal`, `buzzing`, `answering`, `announcing` — составные узлы. Число узлов не является контрактом: ориентир — код машины и именованные ветки ниже. Состояния `buzzing.reminding` в машине нет: так назван только один из путей, с которых «Дальше» возвращает в `buzzing`.

Основной маршрут: `startMenu` → `connecting` → `welcoming` (или `restoring`, если есть снимок) → `choosing` → `flashing` → `reading` → (обычный раунд: `buzzing`/`answering`/оценка → `announcing`) → снова `choosing`, либо `bridging`/`finished`. Финал: `choosing` (удары) → `finalDraft` → `finalBets` → `flashing` → `reading` → `turnCue` → `finalTyped` → `finalReveal` (look → verdict → stakeCue → scoreCue, по кругу за каждого финалиста) → `wrapUp` → `finished`.

Есть и глобальные события: `PAUSE` → `paused`, `STOP` → `stopped`, `CONNECTION_LOST` → `failed`, `RESET_GAME` → `startMenu`, `NEXT_ROUND` → `bridging` или `finished`. Они действуют из почти любого узла; точные запреты — в списке.

Путь обычного вопроса по узлам: `reading.sealed` → (раннее окно) → `reading.armed`; дочитала раньше окна → `afterReading` → (`falseStartCue` по монетке или сразу) → `buzzing.open`; нажали в `armed` или в окне → `answering.waiting` → `answering.hearing` → оценка → `announcing`; из объявления — снова `buzzing` (перехват после ошибки/молчания), `answering` (созвучие), `flashing` (выбирающий кликнул во время комментария) или мост/выбор/конец.

## Узлы

**startMenu.** Меню. Сессии нет, табло партии не показано, кнопки закрыты, часы не идут.

**connecting.** Идёт подключение. Кнопки закрыты, часы не идут. Пустой ключ контроллер сразу превращает в `CONNECTION_FAILED`.

**restoring.** Снимок продолжения. Узел не ждёт: сразу выбирает фазу по `resumePath` и стирает его. Таймеры запускаются входом в восстановленные узлы; отдельная ветка `buzzing.open` явно выставляет полную длительность.

**welcoming.** Ведущая коротко здоровается и зовёт выбрать вопрос. Темы и цены не называет. Табло раунда уже есть, текст вопроса нет. Кнопки закрыты, полоски нет. Микрофон выключен, пока она говорит.

**choosing.** Родитель. На входе гасит вопрос, игрока ответа, услышанное и часы. В финале статус «Выберите тему финала», иначе «назовите тему и стоимость». В финале темы вычёркивают по кругу: удар — это `STRIKE_THEME` от текущего игрока круга (`finalStriker`) или любой `QUESTION_SELECTED` с открытой темой (клик по табло или голос): тема уходит в `struckThemes`, удар переходит по кругу всем игрокам, после удара, оставившего одну тему, — `finalDraft`. Право клика в конференции: `chooserId` или текущий `finalStriker` (мастер проверяет по `clientId`, `canPickCell` — по снимку). Отвал при открытом круге удара — тоже передача: `CHOOSER_OFFLINE` проходится гвардом и для `fromPlayerId === finalStriker` (не только для `chooserId`), `handoffChooser` двигает каждый токен только если он был у отключившегося — ход выбора и право удара идут вместе, пока это один игрок. Кнопка… нет — подсветка табло остаётся у выбирающего; в финале кнопок нет. Дальше всегда один из детей.

**choosing.listening.** Слушает выбор. Микрофон открыт. Кнопки ответа закрыты, полоски нет. Кашель ячейку не открывает: это решает контроллер и либо молчит, либо шлёт `QUESTION_UNCLEAR` или `QUESTION_SELECTED`. На входе контроллер бампит `choiceEpoch`: запоздавший транскрипт прошлой реплики или выбор до `CHOOSER_OFFLINE` ячейку не открывают. В конференции кликать поле может только `chooserId`; микс для модели сужается до выбирающего (если Jitsi id ещё нет — fail open на всех). Подсказка про выключенный микрофон и уточнение выбора идут с `conversation: none`. Если микрофон выбирающего выключен стабильно (`mutedMicStableMs`), обычное напоминание выбора (каждые 20 с) говорит не про темы, а про микрофон: ведущая сама придумывает фразу с именем. Так не больше `mutedChooserMaxReminders` раз за ход; счётчик не сбрасывается при уточнении и возврате в listening, а только при смене выбирающего или включении микрофона. Отдельного цикла нет. Неясный выбор пишет в «Оценку» «Услышала: …» и что нужны тема и стоимость. Это дополнительная реплика: состояние не меняется, часы выбора не появляются. У мастера галка «Меньше слышать» сужает микс модели до выбора/ответа/ставки (вне них — глухо; в лобби — все); статус «Слушаю Имя» / «Ничего не слышу» / «Слушаю всех». На всех конференционных экранах карточка подписана полным именем: «Вася выбирает вопрос» или «Вася выбирает тему финала».

**choosing.resolving.** Больше не используется (с 16 октября 2026): реплики выбора разбираются, пока машина в `choosing.listening`, микрофон не закрывается. Узел оставлен для старых сохранений: вход сразу шлёт `SELECTION_FAILED` → `choosing.listening`.

**Выбор из нескольких реплик (контроллер, `choiceTurn`).** Каждая реплика выбирающего в `choosing.listening` разбирается сама: быстрый локальный путь `matchSpokenCell` или `selectQuestion` (со звуком реплики и всеми прошлыми фразами хода по порядку); прошлые разборы не отменяются, модель — по одной реплике за раз (очередь). Пока игрок говорит (открыт VAD) или хоть одна реплика в разборе — не решаем. Потом с последней реплики назад берём первую, что дала ячейку («берём шутки за 300» + «ну давайте посмотрим что там» → шутки 300) → `QUESTION_SELECTED`. Ни одной ячейки — ведущая молчит `choiceClarifyAfterMs` (3 с тишины, `options.ts`), и только потом `QUESTION_UNCLEAR`; новая речь сбрасывает этот отсчёт. Реплики, на которые уже переспросили, второй раз переспрос не вызывают. Шум (`speech: noise`, эхо подсказки, короткий звук) ячейки не даёт и переспроса не вызывает. Модель не ответила за `choiceResolveTimeoutMs` — реплика «без ячейки». Ход сбрасывается при выходе из `choosing`. Ячейка по одному звуку (расшифровка не успела за `transcriptWaitMs`, модель уверенно назвала ячейку): реплика остаётся «в разборе» ещё до `choiceLateTranscriptMs` (2,5 с) и ждёт расшифровку. Пришла и это эхо подсказки тем или реплики ведущей — реплика становится шумом, ячейка не открывается даже при `confident=true` (дамп 19:28:00.119Z: ячейка открылась, через 58 мс пришло эхо каталога). Пришла обычная речь — ячейка сразу; не пришла — верим модели.

**choosing.clarifying.** Просит назвать ячейку ещё раз. Микрофон открыт: обрывает её подтверждённая речь (≥ `bargeInSustainMs` или расшифровка не пуста и не эхо), голый VAD — нет. В конференции карточка по-прежнему показывает, кто выбирает вопрос или тему финала.

**chooserHandoff.** Только конференция. Выбирающий 10 секунд не шлёт heartbeat. `chooserId` уже передан следующему по кругу подключённому игроку, но выбор закрыт, пока ведущая свободно не объявит отключение и нового выбирающего (`hostCue`: кто ушёл, кто теперь выбирает, вопрос или тема финала). На входе контроллер бампит `choiceEpoch`, чтобы поздний разбор речи прежнего выбирающего не открыл ячейку уже за нового. Отвечающего игрока отключение в этот узел не переводит: его ждут таймауты ответа.

**flashing.** Выбранная ячейка моргает `cellFlashMs`. Текста вопроса на табло ещё нет. Микрофон закрыт. В обычном раунде ранняя кнопка — фальстарт, очки не меняются. В финале фальстарта нет.

**reading.** Родитель. На входе статус «Ведущая читает вопрос», полоска ещё пустая. Текст вопроса уже на табло. Речь комнаты во время чтения ответ не засчитывает; если это не шум и не сам текст вопроса, контроллер ставит `TALKED_OVER`.

**reading.sealed.** С начала чтения идёт раннее окно (`earlyLeftMs` из `earlyBuzzerMsFor` по длине вопроса). Кнопки ответа закрыты. Нажатие в обычном раунде — фальстарт. Полоски окна кнопки нет. В финале раннее окно в `armed` не переходит: ждут конца чтения.

**reading.armed.** Обычный раунд, раннее окно вышло, ведущая может ещё читать. На входе `startArmedBuzzer`: статус «Жмите свою кнопку», полоска стартует на полные `buzzerMs`, `spokeWithoutButton` сбрасывается. Кнопки открыты. Нажатие обрывает её звук. Сигнал за `buzzerWarningMs` до конца этого окна ставит контроллер. Звук и ролик вопроса здесь ещё не играют: клип вопроса молчит всё `reading.*`.

**afterReading.** Чтение обычного вопроса кончилось раньше раннего окна. Узел не ждёт. Если на вопросе был фальстарт и монетка (`falseStartCoin`, около половины) выпала, дальше фраза фальстарта. Иначе сразу полное окно `buzzerMs`. Если `buzzerMs` уже шли в `armed`, этот узел не используется и полоска заново не начинается.

**falseStartCue.** Короткая фраза вроде «Вася, фальшстарт», без ответа пакета. Кнопки открыты, полоски ещё нет: `buzzerMs` стартуют после фразы. Микрофон открыт, пока она говорит: перебивание запоминается для лекции про кнопку. Игрок на штрафе фальстарта по-прежнему не проходит guard. Клип вопроса в обычном раунде здесь играет и крутится.

**bridging.** Между раундами. Ведущая называет имя и счёт каждого и объявляет следующий раунд или финал. Раунд уже переключён, выбирает снова игрок 2, если игроков хотя бы двое, иначе первый. Кнопки закрыты, полоски нет.

**finalDraft.** Ведущая объясняет финал и скрытые ставки. Темы уже вычеркнуты до одной (последний удар переводил сюда через `applyStrike`); круг удара: `finalStriker` начинается от выбирающего финального раунда и крутится по всем игрокам. Полоски нет. `purposeFinalIntro` → `finalBets` (`prepareFinalists`).

**finalBets.** Скрытые ставки, 30 секунд (`deadlineFinalStake`). Финалисты — все игроки, порядок разбора — счёт вверх (при равенстве — по номеру). Каждый финалист печатает ставку на табло (`FinalEntry`, событие `FINAL_STAKE`): целое от 0 до своего счёта, одной ставки достаточно — повторно ставка не принимается. В снимок конференции сумма не идёт: там только `stakedIds`, суммы раскрываются при разборе (`stakes`). Когда напечатали все (`finalAllStaked`) или истёк таймер (`fillMissingStakes` — неуспевшим 0) — `flashing`, тема моргает, на входе `openFinalQuestion` открывает единственную тему. В конференции ставка уходит сообщением `finalStake`, право проверяет мастер. На табло панель «Скрытые ставки»: свои поля ввода, у уже поставивших «Ставка принята», у чужих — «решает ставку».

**turnCue.** Финал. На входе `assignFinalAnswerer` берёт курсор разбора (`finalCursor`) и ставку текущего финалиста в `activeStake` (ставки нет — 1). Ведущая говорит, что отвечает `<имя>` и что ответы — на табло. Кнопок нет, полоски нет. Вопрос заново не читает. `purposeTurn` → `finalTyped`.

**finalTyped.** Скрытые ответы, 30 секунд (`deadlineFinalTyped`). Каждый финалист печатает ответ (`FINAL_TYPED`, до 200 символов, одного хватает). Текст в снимок не идёт до разбора — только факт `typedIds`. Все напечатали (`finalAllTyped`) или истёк таймер (`fillMissingTypedAnswers` — пустые) → `finalReveal`. Кнопок нет.

**finalReveal.** Родитель разбора. От меньшего счёта вверх: `look` → `verdict` → `stakeCue` → `scoreCue` → следующий `look`; последний `scoreCue` → `wrapUp`.

**finalReveal.look.** На входе `assignFinalAnswerer` (текущий финалист) и `showTypedAnswer` (ответ раскрывается в снимке, табло печатает его в полосе разбора); статус — «Смотрим ответ <имя>», без рода. Вердикт: пустой ответ или слово-в-слово совпавший с эталоном (`typedInstantVerdict`, с нормализацией) — машина сама ставит вердикт и сразу уходит в `verdict` (`typedInstantVerdict` guard, `applyTypedVerdict`), модель не звалась; остальное судит контроллер отдельным изолированным текстовым ходом `finalJudge`; не успела модель за `judgeMs` — `verdict` c итогом «счёт не меняется» (`finalJudgeFailed`). Полоса разбора на табло (`FinalRevealStrip`) показывает по каждому финалисту имя, раскрытый ответ, вердикт и названную ставку.

**finalReveal.verdict.** Ведущая коротко вердиктирует по имени (`finalVerdictCue` — только вердикт, без эталона и ставки). `purposeAnnounce` → `stakeCue`.

**finalReveal.stakeCue.** «Смотрим ставку». `purposeStake` → `scoreCue` с `revealFinalStake`: очки меняются открыто в момент разбора (плюс ставки за верный, минус ставки за неверный; ставка 0 счёт не меняет), в снимок уходят `stakeShownIds` и суммы названных ставок (`stakes`).

**finalReveal.scoreCue.** Новый счёт назван. `score` — дальше `look` (`nextFinalist`, `clearJudgment`), если есть кто; последний — `wrapUp`.

**wrapUp.** Финальный счёт и победитель. Полоски нет. `purposeBridge` → `finished`.

**buzzing.** Родитель окна кнопки. Сейчас единственный ребёнок — `open`. Кнопки открыты. Речь без кнопки часы не останавливает и не продлевает.

**buzzing.open.** Полоска уже идёт: полные `buzzerMs` или `stealBuzzerMs`, либо остаток, если окно началось ещё в `reading.armed`. Конец окна закрывает ячейку. В первом окне обычного раунда клип вопроса играет и крутится. В перехвате (`missedIds` не пуст) клип не продолжается. Сигнал предупреждения — только на полном `buzzerMs`, и контроллер не ставит его второй раз, если окно уже шло из `reading.armed`. На входе контроллер бампит `buzzEpoch`: фраза без кнопки из прошлого окна `spokeWithoutButton` не ставит. В конференции устойчивая речь игрока по уровню дорожки (≥1 с, `subscribeSpeechActivity`) без нажатия даёт одно короткое напоминание «ответ только по кнопке» на вопрос (`noBuzzerCue`); не в финале, у игрока из `missedIds` не звучит, часы не трогает.

**answering.** Родитель ответа. Кнопки закрыты. На входе растёт `attemptId`, игрок записан, часы ответа ещё впереди.

**answering.waiting.** Ждёт речь. После кнопки (из `buzzing`/`reading`/`falseStartCue`, без раннего ответа) ведущая коротко зовёт игрока (`buzzCall`, `buzzCallCue`). Если к этому моменту уже есть осмысленная фраза до кнопки (не эхо, не фантом, не пусто), она входит в ту же реплику как контекст: сказано до нажатия, в зачёт не идёт, слова фразы и эталон вслух не повторять; ведущая сама решает, коротко отметить факт или промолчать. Если игрок уже начал ответ, реплика не начинается. Поздняя расшифровка договаривает ту же реплику, только пока имя уже сказано, ведущая молчит и игрок ещё не говорит. Часы `answerMs` от этого не сдвигаются, отдельного состояния нет. Слух уже открыт, начало ответа обрывает обращение. После `ANSWER_ECHO`/повтора обращения нет. Полоска `answerMs` или, после повтора, `clarifyMs`. Микрофон открыт. В попытку входит речь, начатая после открытия попытки, и фраза раннего слуха («повтори», апелляция). Речь чтения, окна кнопки, фальстарта и перехвата до нажатия в попытку не входит: на OpenAI и Grok открытая реплика закрывается `input_audio_buffer.commit` (хвост без реплики — `clear`), в ответ идёт только следующий item. Qwen событие commit получает, но полудуплекс может не разрезать буфер. Gemini commit/clear не делает. На всех проводах item, начатый до нажатия, не оценивается; если провод не разрезал звук, хвост той же реплики в ответ не попадает. Новый item после кнопки тоже не оценивается целиком, если его текст равен последней фразе, уже закрытой до кнопки, или только продолжает её: префикс пишется в чат с пометкой «до кнопки», в оценку идёт хвост, пустой хвост — не ответ. В технической колонке строка «распознаватель подклеил фразу до кнопки…». Grok шлёт несколько `transcription.completed` на одну реплику — в ход берётся финальная, поздняя правка закрытый ход не открывает; у OpenAI по-прежнему одна completed. Инструменты в `response.create` у Grok вложены в `function` (так сервер их принимает); `session.update` остаётся плоским, `function_call_output` — как в документации xAI. Запоздавший VAD чужой прошлой попытки после `silence` по-прежнему не принимается и в чат не пишется. В конференции сообщение активного игрока в чате во время `answering.*` — реплика попытки: контроллер `chatAnswer` по имени принимает его как `AnswerUtterance` с `chatText` (оценка текстом, без эхо/фантомных фильтров, решение после тишины как у речи); чужое сообщение и любое в паузе финале игнорируется. Пока попытка открыта, «Услышано» в чат идёт только после принятия речи; отброшенный транскрипт в колонку не пишется. Исключение — речь до кнопки: строка с бейджем «до кнопки», без оценки. Эхо подсказки Whisper (в т.ч. buzz/reading) и фантом эталона из словаря на коротком VAD / низкой уверенности тоже не реплика игрока (`ANSWER_ECHO`). В конференции карточка показывает «Вася отвечает»; если опубликованный микрофон отвечающего остаётся выключен 3 секунды и свежей речи ответа не было, ведущая один раз за попытку сама придумывает короткую фразу, что микрофон выключен (по имени, тёплый тон, и — в конференции — напомни, что ответ можно написать текстом в чат). Это дополнительная реплика без перехода состояния и остановки часов; начало ответа её обрывает. В финале клип вопроса здесь играет; в обычном раунде на ответе он на паузе.

**answering.settling.** Реплика закончилась, микрофон модели открыт: ждём ещё речь или решение контроллера. Карточка — «Вася отвечает».

Обрыв `buzzCall` отменяет конкретный запрос речи, даже если его `response.created` ещё не пришёл. События воспроизведения связываются с отправкой текущей фразы: запоздалое `stopped` приглашения не завершает последующий вердикт. Подробности и живой случай — [DEBUG.md, «обрыв»](DEBUG.md#обрыв--кто-и-почему-обрывает-ведущую).

**Ответ из нескольких реплик (контроллер, `answerTurn`).** Как выбор ячейки. Каждая законченная реплика попытки получает свою оценку `submitAnswerJudgment` (по аудио или тексту, как раньше; оценки по одной, очередью; новые не отменяют старые); в конференции к репликам равно и сообщение активно отвечающего в чате (контроллер принимает от этого игрока, оценка текстом без эхо/фантомных фильтров). В оценку идут все прошлые реплики попытки по порядку и последняя реплика ведущей. Модель возвращает, кроме `status`, поле `speech` (`answer` — разборчивая попытка ответа; `stall` — заминка, «щас-щас», смех, мычание; `noise` — речи нет, в т.ч. эхо ведущей) и `guessing`. Решение: игрок молчит `answerSilenceDecideMs` (2,5 с) после последней реплики И ни одна реплика не в оценке. Засчитывается строго последний разборчивый ответ: с последней реплики назад, `stall`/`noise` пропускаются. «Пушкин», потом «нет, Лермонтов» — считается «Лермонтов». Перебор вариантов наугад (`guessing: true`, только при почти полной уверенности модели) — не засчитано (`incorrect`), ведущая своими словами подмечает перебор. Пока только шум/заминки — слушаем до общего лимита (`answerMs` = 15 с или `clarifyMs` от кнопки), потом как молчание (`ANSWER_NONE`). Лимит вышел посреди реплики — ждём её конец и оценку (не дольше `answerOverrunSafetyMs`), решаем без паузы тишины. Оценка реплики не пришла за `answerUtteranceJudgeMs` — реплика «без оценки»; если решающая — как таймаут оценки. Кашель во время обращения «Вася, вам слово» обрывает ведущую (она слушает), но это просто реплика `noise`. Эхо подсказки и эхо реплики ведущей (`echoesHost`) — `noise`, без вызова модели. Переответ и оспаривание работают от итогового вердикта.

**answering.hearing.** Игрок говорит. Полоска ответа снята; в конференции карточка продолжает показывать «Вася отвечает». Длинная реплика оценивается, когда кончится (см. пункт 63). Тот же гейт попытки, что в `waiting`.

**judging.** «Ведущая оценивает ответ». Микрофон закрыт. Полоски нет. Оценка — `submitAnswerJudgment` с `conversation: none`; принимается только tool с текущим `turn`, поздний ответ после ухода из `judging` отбрасывается и не трогает уже начатую речь объявления. В текстовом пути транскрипт ждётся только по `itemId` этой попытки: без id контроллер не подхватывает «любой» следующий текст. Потолок `judgeMs`: нет оценки — очки не меняются. Чужой `questionId`, игрок или `attemptId` событие не принимает.

**announcing.** Родитель объявления. Часы сняты, кнопки закрыты. На входе контроллер снимает привязку попытки ответа (`liveAttemptId`), чтобы поздняя речь не ушла в следующий ход. Ответ пакета на табло и вслух — только если ячейка уже закрыта и повод `nobody`, `incorrect`, `silence` или `unclear`. При `silence` (за окно ничего не услышали) реплика не про «неверно»: свободно, что не расслышала / про микрофон, плюс минус очков; при `incorrect` — сухое неверно и минус. При молчании контроллер выдерживает `timeoutBeepMs` и затем даёт ей фразу. Клип вопроса здесь не играет.

**announcing.speaking.** Ведущая говорит решение. Картинка ответа (если есть) уже на табло; звук и ролик ответа ещё не играют.

**announcing.holding.** После конца речи, если у ответа есть медиа: медиа ответа (картинка, звук, ролик) при любом исходе с закрытой ячейкой, и после верного, видны всё объявление и пока играет клип, но не меньше `answerMediaMinMs` (3 с) и не больше `answerMediaMaxMs` (10 с) с момента показа; длинный клип обрезается на 10 с. Клип ответа играет один раз, без цикла; его конец (`ANSWER_MEDIA_ENDED`) отпускает удержание, если min уже прошёл. Без медиа ответа этот узел не входят — сразу выход из `speaking`.

**paused.** Микрофон и звук ведущей выключены локально, таймеры машины не тикают. Фаза, из которой ушли, лежит в `resumePath`. Штраф фальстарта замирает: при продолжении метки сдвигаются на длительность паузы. Остаток раннего окна в `reading.sealed` запоминается. Остаток полоски `buzzerMs` / `stealBuzzerMs` / `answerMs` машина не хранит: «Дальше» ставит полную длительность этого окна заново. Дедлайн контроллера, который ведёт уже начатую реплику (`answering.hearing` / `settling`), после «Дальше» тоже ставится на полную длительность (`answerMs` или `clarifyMs`), не на остаток. Автор 24 октября 2026 подтвердил это окончательно: пауза жмётся редко, полная длительность проще остатка и заодно сбрасывает таймеры. Возврат в `reading.armed` заново выполняет вход и тоже ставит полные `buzzerMs` и статус «Жмите свою кнопку». Пока пауза, контроллер копит конец фразы ведущей и вызовы выбора и оценки; «Дальше» выпускает накопленное. Если фаза после этого та же (например доиграла подсказка про микрофон), микрофон снова открывается для слушающих фаз.

**stopped.** «Остановлена». Сессия и таймеры закрыты, экран партии остаётся. Своих переходов дальше нет. «Пауза» и «Дальше» отсюда не уводят.

**finished.** «Игра закончена». Ведущая называет победителя. Кнопки закрыты.

**failed.** Связь потеряна или старт не удался. Сессия закрыта, экран возвращается в меню с ошибкой. Счёт этой сессии партия дальше не крутит, пока не начнут снова.

## Переходы

**Ранний слух.** Слух открывается в момент, когда табло показало запрос игроку, а не после речи ведущей: `cat.announcing`, `cat.staking.asking`, `auction.announcing` (при автоставке `special.autoStake` реплики при объявлении — не заявки: контроллер их не разбирает), `auction.asking` и `chooserHandoff` (`PLAYER_SPEECH_STARTED` → `choosing.listening`). Ведущая обрывается только валидным ответом; эхо её реплики отбрасывается через `literalRepeat`. Ответ одного игрока по просьбе ведущей тоже слушается сразу: просьба повторить (`announcing.speaking` при `announceKind = repeat`) и повтор при апелляции (`appealCue`) идут при открытом микрофоне. Если ведущая ещё не начала звук, речь сразу шлёт `PLAYER_SPEECH_STARTED` → `answering` и попытка подхватывает ту же фразу. Если она уже говорит, реплика дольше 600 мс (не эхо) обрывает её и делает то же. Ход финалиста (`turnCue`) голосовой ответ не открывает: ставки и ответы финала печатные, реплики при `finalBets` и `finalTyped` просто пишутся в разговор. Если модельная VAD не прислала `speech_started`, а уровни микрофона видели реплику того, кто сейчас говорит (ответ, выбор ячейки, кот, ставка, просьба повторить), контроллер один раз на это окно делает запасной `input_audio_buffer.commit` (`answerSilentCommit`). На «повтори» попытка открывается до commit. На автоставке аукциона при объявлении commit не делается. Уже открытую моделью реплику второй раз не коммитим. Чтение вопроса и правила кнопки не менялись (речь во время чтения — эхо, если ≥60% слов расшифровки из вопроса или совпала с репликой ведущей; иначе `TALKED_OVER`); hearTurnOnly сохраняется (микс модели сфокусирован на игроке для всего корня фазы).

Один и тот же `HOST_AUDIO_FINISHED` с чужим `purpose` состояние не меняет. Ниже — только то, что машина принимает. Нумерация ниже — ссылки внутри документа, не подсчёт переходов: есть пункты с буквами и несколько guard в одном пункте.

### Из любого узла

1. `RESET_GAME` → `startMenu`. Контекст заново, демо-пакет.
2. `CONNECTION_LOST` → `failed`. В контекст пишется текст ошибки и «Связь с ведущей потеряна». Контроллер не шлёт это из `startMenu`, `connecting`, `failed` и `stopped`.
3. `PAUSE` → `paused`, если это не `paused` и не `stopped`. Запоминает путь и статус, гасит полоску, замирает фальстарт.
4. `STOP` → `stopped`, если это ещё не `stopped`. Статус «Остановлена», часы гаснут.
5. `NEXT_ROUND` → `bridging`, если партия живая и следующий играбельный раунд есть. Раунд переключается сразу, узел моста входится заново.
6. `NEXT_ROUND` → `finished`, если партия живая, а следующего раунда нет. Вопрос и финальные ставки стираются, сыгранные id остаются.
   Живая партия — всё, кроме `startMenu`, `connecting`, `failed`, `stopped`, `finished` и паузы, снятой уже с конца.

### Меню и связь

7. `startMenu` + `START_GAME` → `connecting`. Пакет и имена становятся партией.
8. `startMenu` + `CONTINUE_GAME` → `connecting`. Поверх пустой партии ложится снимок, включая `resumePath`.
9. `connecting` + `CONNECTED`, `resumePath` не пуст → `restoring`.
10. `connecting` + `CONNECTED`, снимка нет → `welcoming`.
11. `connecting` + `CONNECTION_FAILED` → `failed`.
12. `failed` + `START_GAME` → `connecting`.
13. `failed` + `CONTINUE_GAME` → `connecting`.
14. `welcoming` + `HOST_AUDIO_FINISHED` purpose `welcome` → `choosing`.

### Восстановление снимка

Вердикт (`judgmentStatus`, `announceKind`) сохраняется при восстановлении `finalReveal.verdict`/`stakeCue`/`scoreCue`: до раскрытия ставки он нужен для начисления, после — для верного отображения. Сквозная проверка живых состояний машины, сетевого снимка, записи/чтения localStorage и новой машины — `src/game/finalRestore.test.ts`; итоговый счёт после восстановления на каждом шаге не меняется повторно.

### Выбор ячейки

`QUESTION_SELECTED` смотрится сверху вниз.

29. `choosing.listening` + `PLAYER_SPEECH_FINISHED` → `choosing.resolving`.

### Оценка

66. `judging`, прошло `judgeMs` → `announcing`, повод `unclear`. В обычном раунде итог попытки 0 (заменяет прежний итог пары, см. «Апелляции»), игрок в `missedIds`, ячейка остаётся открытой, если ещё есть кому жать. В финале ячейка закрывается только на последнем финалисте. Фразы про близость нет. Когда ячейка закрылась, ответ пакета публикуется, как при `nobody`. Пока ячейка открыта, его нет.
67. `judging` + `ANSWER_ECHO` → `answering`. Оценка отброшена, окно ответа начинается заново.
68. `judging` + `ANSWER_JUDGED`, тот же вопрос, игрок и попытка → `announcing`. Дальше правила счёта.

До передачи оценки в машину текстовый судья должен вернуть в `heard` всю исходную реплику, без перевода, сокращения или исправления под эталон (регистр, пробелы и обычная пунктуация несущественны). Если он вернул `correct`, но подменил текст, контроллер через `settleJudgment` снимает зачёт до `ambiguous`; обычный раунд даёт 0, финал обрабатывает неопределённость как неверный ответ. Без исходного текста `heard` модели не заменяет расшифровку. В финале источник — сохранённый `typedAnswers` отвечающего. Точное совпадение исходной реплики с эталоном по-прежнему проверяется независимо от модели; аудиосудья оценивает собственный `heard`, сравнение с ASR к нему не применяется.

Что делает принятая оценка:

- `correct`: плюс номинал или ставка. В обычном раунде ячейка закрывается. В финале ячейка закрывается только если это последний финалист. Выбирает следующий вопрос этот игрок. Ответ пакета не публикуется. Повод `correct`.
- `incorrect`: минус номинал или ставка. Игрок в обычном раунде в `missedIds`. Ячейка остаётся, если ещё есть кому жать. Иначе закрывается по тому же правилу финала. Выбирает этот игрок. Повод `incorrect`. Если ячейка закрылась и в `wrongHeard` есть непустая реплика, монетка решает, говорить ли, что попытка была близкой.
- `near_miss`, и повторов ещё меньше `maxClarifications`: очки те же, ячейка открыта, выбирающий не меняется, `clarifications` плюс один. Повод `repeat`. Следующий `near_miss` сверх лимита машина считает `incorrect`.
- `unintelligible`, `ambiguous`, `needs_clarification`: итог попытки 0. В обычном раунде игрок в `missedIds`, ячейка остаётся, если ещё есть кому жать (перехват 5 секунд), выбирает этот игрок. Повод `unclear`. Когда ячейка закрылась, ответ пакета публикуется. Пока ячейка открыта, его нет. В финале — прежнее поведение.

`wrongHeard` пополняется только настоящим `incorrect`, без причины «созвучие уже переспрашивали».

### Пауза, «Дальше»

`RESUME` возвращает ровно сохранённый путь. Часы заново, полной длительностью, получают только пути из `showsClock`: `buzzing`, `buzzing.open`, строка `buzzing.reminding`, `answering.waiting`. ## Конференция

Транспорт состояния не добавляет переходов XState: мастер сначала/по `statusRequest` шлёт общий полный `snapshot`, дальше `partialUpdate` изменённых полей. Joiner до первого статуса ждёт мастера и повторяет запрос; чужой ответ на запрос тоже становится его текущим состоянием. При пропуске ревизии он запрашивает полный статус. Секундный пустой диф — heartbeat. Реплики идут отдельными дифами одного из 200 слотов и `messageIndex`, не воздействуют на машину. Весь буфер синхронно сохраняется при каждой записи, включая лобби/паузу. Продолжение мастера восстанавливает слоты и индекс до первого полного статуса; отдельного состояния XState для истории нет. Id соединений Jitsi (`jitsiIds`, `hostJitsiId`, `soundsJitsiId`) тоже лежат в снимке рядом с `presence`, а не в контексте машины: игровая логика их не читает. Подробный wire-формат — [ONLINE.md](ONLINE.md).

Лобби до `START_GAME` машину не запускает: мастер в комнате, игроки качают пакет и жмут «Я готов», снимок фазы `lobby` идёт по каналу. При этом React-слой отдельно пишет в `aisigame.game` минимальный снимок с `conferenceLobby: true`, roomId, пакетом и мастером; это не переход XState. После `START_GAME` снимок лобби заменяется обычным снимком машины без этого флага, подписка машины и периодический heartbeat рассылают дифы текущего состояния машины; повторный `hello`, `ready` или тик присутствия не возвращает удалённые экраны в `lobby`. После старта партии правила те же, что за столом; у мастера крутится эта машина.

Продолжение снимка с `conferenceLobby: true` снова открывает ту же комнату как лобби и не отправляет `CONTINUE_GAME`. При продолжении уже начатой конференции мастер восстанавливает `CONTINUE_GAME` в той же комнате и сразу рассылает восстановленный путь; нового лобби и приветствия нет. Игрок, который увидел уже игровую фазу до получения пакета, автоматически отправляет `ready` после проверки sha256. При смене endpoint мастера он повторяет `hello` и `ready`, поэтому кнопка не теряется в коротком окне после перезагрузки. `CONNECTION_LOST` от активного Jitsi закрывает конференцию и `RESET_GAME` возвращает React-экран в меню.

Сверка пакета тоже не является состоянием XState. Глобальный статус содержит описание пакета и hash: joiner сам сверяет кеш или запрашивает передачу (`packAck: 0`). Начало/сверка (`packStatus`) и новый endpoint игрока снимают прежние hashOk/ready, сбрасывают старые ACK/peer, но не меняют состав, счёт или фазу машины. Heartbeat прежнего endpoint прогресс не сбрасывает. После совпадения sha256 и успешного разбора joiner отправляет `packVerified`; мастер меняет только roster (`hashOk`, 100%), сразу рассылает диф presence, а `ready` остаётся отдельным действием пользователя. Повторный offer того же проверенного пакета повторяет `packVerified`, чтобы обновившийся мастер не застрял на 99%. `debugLog` игрока вообще не меняет машину или снимок: мастер лишь добавляет проверенный ограниченный батч в память debug dump.

Раз в секунду мастер сверяет `chooserId` с presence. Только в `choosing.*`, когда выбирающий `stale` не меньше 10 секунд, `MasterSession` выбирает следующего по кругу из присутствующих и проверенных игроков и шлёт `CHOOSER_OFFLINE`; в финале при открытом круге удара тот же проход проверяет и `finalStriker` (если он другой игрок и тоже затих — шлёт второе событие от его имени). Отсутствующему после восстановления партии тоже дают полный `PRESENCE_STALE_MS`. В других фазах, включая `answering.*`, presence снимок обновляет, но событие машине не шлёт.

### `ADD_PLAYER`

Событие `ADD_PLAYER` с полем `player` (в том числе `clientId`) добавляет игрока в `context.players`, если такого `clientId` ещё нет. Фаза не меняется. Счёт у нового игрока задаётся при добавлении (обычно 0). Повтор с тем же `clientId` игрока не дублирует.

В finalBets.* конференция фокусирует микс модели на finalists[finalCursor] независимо от галки «Меньше слышать». Переходы и таймеры ставок не изменены.

13 октября 2026: по решению автора удалён speechSynthesis и localSpeech. После одного неуспешного повтора точной фразы моделью или таймаута неверный звук сбрасывается и посылается обычное завершение чтения; текст пакета остаётся на экране. Состояния/таймеры XState не менялись. Задача передачи браузерного TTS игрокам удалена из to-do.

Публичный контекст свободных реплик передаётся контроллером и не добавляет состояний/таймеров. Judge/selection/read не получают историю чата. Оценка может принять альтернативный фактически верный ответ вне списка эталонов, с проверкой исходного вопроса и прежними id/attempt/turn guards.


### Кот в мешке и аукцион (13 октября 2026)

Контекст: `special: SpecialState | null` — `kind` (`cat`/`auction`), `questionId`, `giverId`, `recipientId` (у кота получатель, на аукционе — кого спрашиваем), `stakeOptions`/`stake` (кот), `nominal`, `order`/`passed`/`leaderId`/`bid`/`allIn`/`options`/`autoStake`/`log` (торги), `unclear` (причина переспроса), `awayPlayerId`/`awayFrom`/`awayNextChooser` (ожидание). Сохраняется в `SavedMatch.special`, проверяется `readSpecialState` и валидатором снимка конференции.

```
choosing ──QUESTION_SELECTED [selectedCat]──▶ cat.announcing ──(cat)──▶ cat.picking ⇄ cat.clarifying
                                                   │ (получатель уже известен)          │ CAT_RECIPIENT
                                                   ▼                                    ▼
                                             cat.staking.asking → listening ⇄ clarifying ──CAT_STAKE──▶ cat.placed → flashing
choosing ──QUESTION_SELECTED [selectedAuction]─▶ auction.announcing → asking → listening ⇄ clarifying
                                                   ▲            AUCTION_BID ▼
                                                   └────────── advancing ──(последний)──▶ won → flashing
```

- `flashing` → `reading.sealed` → по концу чтения сразу `answering` (`beginSpecialAnswer`): `activePlayerId` = получатель, `activeStake` = ставка. Кнопки не открываются (`othersCanBuzz`, `canFalseStart`, `earlyBuzzAllowed` ложны для спецвопроса), неверный ответ закрывает ячейку. Ранний выбор ячейки из `announcing` тоже идёт через `selectedCat`/`selectedAuction`.
- `cat.picking`, `cat.staking.listening`, `auction.listening` — микрофон открыт, слушаем одного (`specialListenerId`); контроллер сам разбирает речь (`matchSpokenPlayer`, `matchCatStake`, `matchAuctionSpeech`) и шлёт событие либо `*_UNCLEAR` → узел `clarifying` (переспрос поверх слушания).
- `SPECIAL_PLAYER_OFFLINE {playerId, nextChooserId}` (шлёт мастер по присутствию; из `cat.staking`, `auction.asking/listening/clarifying`, `answering`/`judging`) → `specialAway`, таймер `catAwayWaitMs`. `SPECIAL_PLAYER_BACK` возвращает в `cat.staking`, `auction.asking` или заново в `answering`. По таймеру: на торгах — `auction.advancing` с автопасом; иначе `announcing` с `announceKind: 'away'`, 0 очков, эталон публичный, выбирает `awayNextChooser`.
- `CHOOSER_OFFLINE` в коте до выбора получателя → `handoffCatGiver` (право отдать следующему, снова `cat.announcing`); на аукционе до первой ставки → `auctionAutoOpen` (номинал за выбравшего). Автоставка (`special.autoStake`: денег ≤ номинала или открывший отключился) помечает торги: пока в `auction.announcing` идёт объявление, реплика игрока — не заявка, контроллер её не разбирает (`considerSpecial` выходит сразу), а машинальные `PLAYER_SPEECH_FINISHED`/`AUCTION_UNCLEAR` отбрасывает гвардой `auctionAutoStake`; после объявления перекупка идёт как обычно. Реплика при объявлении до фикса (18 окт) затягивала торги в цикл `resolving/clarifying/listening` с пустым набором вариантов.
- Пауза и восстановление: пути `cat.*`, `auction.*`, `specialAway` в снимке канонизируются; `RESUME`/restore идут в узлы `cat.resume`/`auction.resume`, которые по `special` выбирают нужный узел (и перезапускают часы ожидания).
- Апелляции: `hasAppeals`/`openAppealNow` работают и для кота/аукциона. Ячейка уже закрыта, поэтому окно сразу `closed` (подтверждение). `settleOutcome` пишет `stake` (= `activeStake`) в итог, `acceptAppeal` возвращает её в `activeStake`, `confirmClosedAppeal` начисляет `appealStake` (ставка или номинал).
- Голос — по образцу `choosing.listening → resolving → clarifying`: `cat.picking → cat.resolving`, `cat.staking.listening → cat.staking.resolving`, `auction.listening → auction.resolving` по `PLAYER_SPEECH_FINISHED` (локально не узнали). В `resolving` микрофон закрыт, контроллер шлёт изолированный `selectCatRecipient` / `resolveSpecialBid`; ответ — то же событие, что и клик, `*_UNCLEAR` → `clarifying`, `SELECTION_FAILED` или `judgeMs` → обратно слушать. Подсказка распознаванию — варианты (`playersPrompt` / `optionsPrompt` в `choicePrompt.ts`), эхо отсекает `echoesChoicePrompt`. Сохранение/RESUME сводит `*.resolving` к `cat.resume` / `auction.resume`. Финал голосового разбора не имеет: ставки и ответы печатные. Ответ на вопрос с вариантами: подсказка распознаванию — все варианты (буква и текст), не только эталон.
- Конференция: клик гостя — сообщение `specialPick` (`player`/`stake`/`auction`). Мастер принимает `player` только от дарителя, ставку — с `playerId` отправителя, вариант аукциона ищет в своём `special.options`.

### Апелляции обычного вопроса (13 октября 2026)

Финал не затронут: там `outcomes` и `appeal` не заполняются, счёт меняет `changeScore`.

Контекст: `outcomes[questionId][playerId] = { amount, attemptId, correct }` — один текущий итог пары (−номинал, 0, +номинал). `settleOutcome` начисляет `новый − прежний`; результат с `attemptId` не новее сохранённого ничего не меняет. `appeal` — текущее окно: `questionId`, `windowId` (из счётчика `appealSerial`), `stage` (`open` — вопрос ещё открыт, `closed` — после закрытия), FIFO `queue`, `activePlayerId`, `lastPlayerId` (право в окне перехвата), сохранённый `chooserId`, `remainingMs`/`startedAt` (`appealWindowMs` = 7 000 — общий размер обоих окон, пауза хранит остаток). Право (`eligibleAppealPlayers`): есть итог по вопросу, `amount ≤ 0`, не `correct`. У заявки `appealRequestError` окно открыто во всём `announcing` (включая `announcing.holding`) — кнопка не мигает во время удержания медиа ответа.

Термины: **переответ** — `stage: open`; **оспаривание** — `stage: closed` (`appealConfirm`) в **окне при выборе** (`choosing.*`) или **окне итогов** (`roundSummaryWindow`).

Новые узлы:

- `afterQuestion` — развилка после объявления закрытого обычного вопроса (и после `announcing.holding`). Если есть право: последний вопрос раунда → `roundSummaryWindow`, иначе → `choosing` с открытым окном `closed` (`openClosedAppeals`). Без права — прежние ветки (`bridging` с `advanceRound`, `finished`, `choosing`).
- `roundSummaryWindow` (**окно итогов**, бывш. `appealWindow`) — только последний вопрос раунда: 7 секунд, `roundIndex` не меняется, финалистов не собирают. Если дальше есть раунд, `appeal.summary = 'pending'` и контроллер говорит `roundSummary` (раунд окончен, счёт каждого, «впереди второй/третий/финальный раунд», кто выбирает). По `appealLeft`, пока итог ещё звучит, окно закрывается для заявок (`timeUp`), фраза дослушивается; `HOST_AUDIO_FINISHED` purpose `roundSummary` после этого → `appealEnd`. `appealEnd` после сказанного итога → `choosing` с `advanceRound` (мост `bridging` не повторяется); без итога — прежние `bridging`/`finished`/`choosing`. Заявка во время итога прерывает его; после серии окно и итог с новым счётом начинаются заново. Статусная строка называет фактическую длину окна («Апелляции · 7 секунд»).
- `appealCue` (**переответ**) — ведущая по имени просит повторить ответ, вопрос не перечитывает. `HOST_AUDIO_FINISHED` purpose `appeal` → `answering` с новой `attemptId` и обычными таймерами.
- `appealConfirm` — заявка `closed` (ответ уже объявлен): `confirmClosedAppeal` ставит +номинал без переответа, через 1 мс → `announcing` (короткая реплика о решении). Контроллер обрывает текущую речь.
- `announcing` на входе (`openAppealNow`): минус при открытой ячейке — окно `open` для этого игрока; ячейка закрыта — окно `closed` для всех с правом (старое окно `open` заменяется). Поэтому кнопка доступна уже во время объявления.
- `appealNext` — после объявления результата апелляции в серии `closed`: следующий из `queue` → `appealCue`, иначе → `afterQuestion` (новое 7-секундное окно, если ещё есть право).

Путь апелляций текстом: объявление (`announcing`, 0/минус при открытой ячейке или закрытый вопрос) → `appealCue` (переответ, заявка от `lastPlayerId`) → `answering`; `afterQuestion` → `choosing` (окно closed) или `roundSummaryWindow` (последний вопрос); из этих окон заявка → `appealConfirm` либо, в серии, `appealNext` → `appealCue` (очередь не пуста) или `afterQuestion` (очередь пуста); `roundSummaryWindow` по `appealLeft` → `appealEnd` → `bridging`/`finished`.

Переходы `APPEAL_REQUESTED` (из любого узла, кроме `paused`/`stopped`/`failed`, только если `validAppeal`: тот же `questionId`/`windowId`, есть право, игрок ещё не в серии):

- серия `closed` уже идёт → в конец `queue` (`queueAppeal`), один playerId — одно место;
- `buzzing.*` при `stage: open` и только от `lastPlayerId` → `appealCue` (`acceptAppeal`), окно перехвата прекращается;
- `buzzing.*`/`announcing` при `stage: open` → `appealCue`; `choosing.*`, `roundSummaryWindow` или `announcing` при `stage: closed` → `appealConfirm` (без переответа); контроллер увеличивает `choiceEpoch`, поздний `selectQuestion` не откроет ячейку.

Закрытие окна: `BUZZER_PRESSED` другого игрока (`assignAnswerer`) и `QUESTION_SELECTED` (`openQuestion`) обнуляют `appeal`; `choosing` по `appealLeft` (guard `idleClosedAppeal`) снимает окно, выбор продолжается; `advanceRound`, `clearActivePlay` (пропуск раунда), `STOP`, ошибка связи тоже обнуляют. `reopenBuzzers` после 0/минуса открывает окно `stage: open` с `lastPlayerId`. В серии `closed` `chooserId` не меняется, `playedIds` не трогается.

Табло: пока `appeal.stage === 'closed'`, экран показывает табло вместо карточки вопроса; ячейки неактивны вне `choosing`. Объявление апелляции получает фактическое изменение (`outcomes[...].previous`): при нулевой разнице ведущая говорит, что апелляция результат не изменила, и не говорит об обновлении счёта.

Пауза: `rememberPause` сохраняет остаток окна, `RESUME` в `appealCue`/`roundSummaryWindow` возвращает туда же. Пауза в `appealConfirm` (шаг в 1 мс) по `RESUME` идёт сразу в `announcing`: вердикт уже записан. Снимок хранит `outcomes`, `appeal`, `appealSerial`; восстановление `answering.*` с активным апеллянтом идёт через `appealCue`; окно чужого раунда отбрасывается; старые снимки без полей — без апелляций.

Реплика итога апелляции (`announceInstructions`, ветка апелляции): подсказке передаются факты (принята ли, игрок, было/стало за этот вопрос, общий счёт) и требование назвать числа точно; формулировка свободная, образца фразы нет; «счёт не изменился» без числа не говорится. Подсказка повтора ответа (`appealCue`) называет текущий итог за вопрос и что новый ответ его заменит.

Поздняя расшифровка (24 октября 2026): событие `LATE_TRANSCRIPT_CREDIT` из любого живого узла, пока `questionId` — это `lateCreditQuestionId` и раунд не финал. Пока ячейка открыта, это `activeQuestionId`. На табло после закрытия он пустеет (`setChoosingStatus`), и окно держится за последнюю сыгранную ячейку, пока `openQuestion` не откроет следующую. `creditLateTranscript` меняет только итог этого игрока на плюс номинал/ставку (`appealStake`) и счёт на разницу; чужие `outcomes` не трогает. Уже `correct` — событие пустое, второй раз очки не прибавляются. Фаза не меняется. Контроллер шлёт событие, когда расшифровка реплики ответа целиком совпала с эталоном (`transcriptIsEtalon`), а итог игрока уже есть и не верный. Строка чата — как у принятой апелляции; речь ведущей (`lateCredit`) не двигает машину и не перебивает ответ, оценку, объявление вердикта, итог раунда и мост.

### Уточнение judging: нативное аудио (13 октября 2026)

Новых узлов нет. На обычном вопросе `?judge=audio` для поддержанной OpenAI-модели внутри judging ждёт подтверждение server audio item до 1500 мс и оценивает его reference, не ASR. Readiness входит в 12-секундный audio budget; техническая ошибка/таймаут даёт ровно один text fallback в оставшемся judgeMs. Unintelligible/ambiguous/incorrect — содержательные результаты, fallback по ним нет. Audio result валиден только с текущими session/reference/request/turn/question/player/attempt; поздний результат после отмены не меняет счёт. ASR-confidence не влияет на audio, heard берётся из аудиооценки.

На PAUSE локальные budgets замирают, готовый результат удерживается. RESUME сохраняет прежнее поведение машины: заново полный judgeMs; оставшиеся readiness/audio бюджеты продолжаются, уже отправленный primary не повторяется. STOP/NEXT_ROUND/смена вопроса очищает runtime waits/results. Shadow — независимая debug-оценка, фаз/счёта не меняет. Аудио включено по умолчанию по решению автора, с UI-переключателем на text; финал и неподдержанные провайдеры всегда text. Канонизация judging→answering.waiting при restore не менялась: audio references в новой API-сессии не продолжаются.

### Молчание игрока (14 октября 2026)

`choosing.listening`, `cat.picking`, `cat.staking.listening`, `auction.listening` имеют `after: idleStep` (задержка из `context.idle`): промежуточные пороги — переход сам в себя с `idleNudge` (реплика ведущей), последний — `idlePassChooser` → `chooserHandoff`, `idleGiveCat` → `cat.staking`, `idleMinStake` → `cat.autoStaked` → (`HOST_AUDIO_FINISHED idleAuto`) → `cat.placed`, `idleAuctionPass` → `auction.advancing`. События `IDLE_SPEECH` и `HOST_TALKING` в этих узлах — переход сам в себя (`reenter`), который копит или сбрасывает тишину и перевзводит таймер; в остальных узлах они только обновляют `context.talk`. Подробности — [GAME.md](GAME.md#молчание-игрока-14-октября-2026).
